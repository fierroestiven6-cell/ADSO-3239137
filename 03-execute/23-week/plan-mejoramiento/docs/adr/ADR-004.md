# ADR-004: Database Engine Selection

- **Project:** Mobility Aids
- **Status:** Accepted
- **Date:** 2026-11-08
- **Reviewed:** 2026-11-26 (decision unchanged)
- **Decision Makers:** Mobility Aids Project Team

## 1. Context

Mobility Aids requires a relational database to manage technical aid categories, technical aids, beneficiaries, loans, loan details, returns, inventory availability, and historical records.

The database must preserve data integrity and support concurrent operations. In particular, when multiple users attempt to borrow the last available unit of a technical aid, only one operation must succeed.

The system architecture defines Laravel as the backend framework and Docker as the containerization solution. The logical data model is documented in `data-model.md`, while ADR-002 establishes the inventory concurrency requirements.

The database engine had not been explicitly selected in the previous architecture decisions. Therefore, a specific relational database management system must be established.

## 2. Decision

The project will use **MySQL 8.4 LTS** as its relational database management system.

The database will use the **InnoDB** storage engine to support:

- ACID-compliant transactions.
- Referential integrity through foreign keys.
- Row-level locking for concurrent operations.
- Consistent inventory updates.

The database will run as a Docker container using the `mysql:8.4` image.

The Laravel backend will connect to MySQL through its database connection configuration and environment variables.

## 3. Alternatives Considered

### Option A: MySQL 8.4 LTS — Selected

**Advantages:**

- Supports ACID transactions through InnoDB.
- Supports row-level locking for concurrent inventory operations.
- Integrates with Laravel.
- Provides a relational structure suitable for the project's entities and relationships.
- The `mysql:8.4` Docker image is available for the development environment.

**Disadvantages:**

- Requires correct transaction and locking implementation to prevent inventory inconsistencies.
- Requires database configuration, backups, and maintenance.

### Option B: PostgreSQL 16

**Advantages:**

- Supports ACID transactions and row-level locking.
- Integrates with Laravel.
- Provides advanced relational database capabilities.

**Disadvantages:**

- Would require a different database image and configuration for the selected development environment.
- Does not provide a necessary advantage that justifies changing the selected database setup for this project.

## 4. Rationale

MySQL 8.4 LTS was selected because it satisfies the project's relational data, transaction, and concurrency requirements while maintaining a straightforward development environment.

The InnoDB storage engine provides transactions and row-level locking mechanisms that can support safe inventory allocation. This is particularly important for implementing the concurrency rule established in ADR-002.

The selection also provides a consistent database platform for Laravel migrations, application queries, and Docker-based deployment.

## 5. Consequences

### Positive Consequences

- The project has a defined relational database management system.
- Laravel database migrations can target MySQL.
- Inventory operations can be executed within database transactions.
- Row-level locking can help prevent concurrent requests from allocating the same last available unit.
- The database can run as part of the Docker infrastructure.

### Trade-offs and Responsibilities

- The team must configure MySQL credentials through environment variables.
- Database credentials and `.env` files must not be committed to the repository.
- The team must implement and test transaction boundaries and locking behavior.
- Database backups and persistent storage must be considered in the infrastructure configuration.
- The physical schema, indexes, constraints, and migrations must follow the approved logical data model.

## 6. Implementation Guidelines

1. Configure MySQL 8.4 LTS using the InnoDB storage engine.
2. Configure the Laravel backend to connect to MySQL through environment variables.
3. Define the physical database schema through Laravel migrations.
4. Execute inventory allocation and loan creation within a database transaction.
5. Use an appropriate locking strategy, such as `SELECT ... FOR UPDATE`, when checking and allocating available inventory.
6. Ensure that a failed transaction does not leave inventory partially modified.
7. Return HTTP `409 Conflict` when a concurrent request cannot allocate the requested last available unit, as established in ADR-002.
8. Add automated tests for concurrent inventory allocation and data consistency.
9. Include the database service in the Docker infrastructure so the environment can be started using the project's documented single-command workflow.

This decision complements the following architecture decisions:

- **ADR-001:** Mandatory Technology Stack.
- **ADR-002:** Inventory Concurrency Control.
