# ADR-003: Historical Records and Logical Deletion

**Project:** Mobility Aids  
**ADR ID:** ADR-003  
**Status:** Accepted  
**Date:** 2026-11-08
**Reviewed:** 2026-11-26 (decision unchanged)

------------------------------------------------------------------------------------------------------------------------

## 1. Context

Mobility Aids manages technical aid loans, returns, and catalog records.

Historical information must remain available even when catalog information changes.

The project requirements establish that loan operations and returns cannot be physically deleted and that catalog records must use logical deletion.

Additionally, historical information recorded at the time of a lending operation must remain unchanged when the original catalog record is modified.

The logical data model defines historical snapshots in `LoanLine`, including the technical aid reference and category recorded at the time of lending.

## 2. Decision

The system will preserve historical loan and return information.

The following rules must be enforced:

- Loan operations cannot be physically deleted.
- Return records and return information cannot be physically deleted.
- Technical aids must use logical deletion or deactivation instead of physical deletion.
- Historical operation data must preserve the relevant information from the time of the transaction.
- Changes to catalog information must not modify previously recorded historical snapshots.
- Historical loan and return information must remain available for consultation and reporting.

Return information is associated with its original loan line through the `returned_at` attribute defined in the logical data model.

## 3. Rationale

Preserving historical records provides traceability and maintains the integrity of past transactions.

Logical deletion allows the catalog to stop presenting inactive technical aids without destroying historical references.

Historical snapshots ensure that previous operations remain consistent even when catalog information changes.

Maintaining return information within its original loan line also preserves the relationship between the lending operation and its return history.

## 4. Consequences

### Positive consequences

- Preserves transaction history.
- Maintains historical consistency.
- Supports auditing and traceability.
- Prevents accidental loss of operational records.
- Allows inactive catalog items to remain referenced by historical transactions.
- Preserves the original technical aid information associated with each loan.

### Constraints

- Physical deletion of loans and return information is prohibited.
- Catalog deletion must be logical.
- Historical snapshots must remain unchanged.
- Database relationships must preserve historical integrity.
- Return information must remain associated with its original loan line.
- Catalog modifications must not compromise previously registered transactions.

## 5. Compliance

All persistence operations must respect this decision.

Automated tests must verify:

- Historical loan records remain available.
- Return information is preserved.
- Technical aids can be deactivated without destroying historical references.
- Historical snapshots remain unchanged after catalog modifications.
- Prohibited deletion operations cannot occur.

The implementation must remain consistent with the project constitution, approved specification, and logical data model.
